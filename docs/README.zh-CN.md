# Orally 文档

[English](README.md) | [简体中文](README.zh-CN.md)

> Status: Reference

此目录将当前实现事实、进行中的重构工作、稳定的产品语言和延期的设计决策分开管理。一份文档写得很详细，并不意味着其中描述的功能已被列入计划。

## 阅读顺序

1. 阅读仓库的 [README](../README.zh-CN.md)，了解当前已经存在的命令和行为。
2. 阅读[重构架构基线](engineering/refactor-baseline.zh-CN.md)，了解当前重构的范围、约束和顺序。
3. 为产品概念命名时，阅读 [CONTEXT](../CONTEXT.zh-CN.md)。
4. 变更某项决策前，阅读涵盖该决策的相关[已接受 ADR](adr/)。
5. 阅读[产品文档](product/README.zh-CN.md)，了解产品意图、隐私方向和延期的可能性。

## 各类问题的权威来源

没有任何一份文档能够覆盖并凌驾于所有其他文档之上。应根据所提问题的类型，使用负责该类问题的来源：

| 问题 | 来源 |
| --- | --- |
| 仓库当前能做什么？ | 代码、现有测试和根目录 [README](../README.zh-CN.md) |
| 某个产品术语是什么意思？ | [CONTEXT](../CONTEXT.zh-CN.md) |
| 为什么做出某项困难的架构选择？ | 相关的已接受 ADR |
| 当前重构的范围是什么？ | 获得批准后的[重构架构基线](engineering/refactor-baseline.zh-CN.md) |
| 预期的用户价值和隐私方向是什么？ | [产品文档](product/README.zh-CN.md) |
| 当前授权了哪些工作？ | 唯一的 Active 基线；GitHub Issues 只是候选项，不代表授权 |

当来源之间存在冲突时，不要静默合并它们的含义。应在 Active 基线中记录冲突，并在改变行为前解决冲突。

当某项功能进入实现阶段时，已接受的 ADR 会约束该功能。但它不会自动把该功能纳入当前里程碑。如果底层决策发生变化，必须用新的 ADR 取代原先已接受的 ADR。

## 文档状态

- **Draft**：等待用户评审的拟议内容；不授权实现。
- **Active**：指导当前工作。
- **Reference**：当前工作必须遵守的稳定上下文。
- **Deferred**：明确置于当前范围之外。
- **Historical**：保留用于说明决策的演进过程。

## 语言政策

- 现有英文路径为 canonical，包括 `README.md`、`privacy.md` 和 ADR 文件名。
- 简体中文配对文件使用 `.zh-CN.md` 后缀，例如 `README.zh-CN.md` 或 `privacy.zh-CN.md`。
- 仓库自有的用户、产品、工程和决策文档以英文/中文配对维护。`.agents/` 下仅供 agent 使用的文件保持英文，避免机器指令发生漂移。
- `docs/product/grilling/README.md` 目录指南采用双语配对。单次探索性的 Grilling 产物可以只保留英文，直到其中的结论被提升到产品文档、基线或 ADR 中。
- Status 值、命令、路径、配置键、环境变量、错误文本和代码标识符在不同语言中保持不变。
- canonical 文档及其翻译的语义变更应归入同一项可评审变更。

在仓库根目录运行文档契约检查：

```powershell
.\scripts\check-docs.ps1
```

## 变更纪律

实现新的产品能力前：

1. 重新阅读产品定义和隐私文档。
2. 在 [CONTEXT](../CONTEXT.zh-CN.md) 中核对相关术语。
3. 核对该领域已接受和已取代的 ADR。
4. 在 Active 基线中更新问题、范围和明确的非目标。
5. 完成上述步骤后，才能开始实现。

已完成的共享语音里程碑只改变了内部职责归属，没有增加面向用户的行为。随后的双语文档里程碑建立了配对的评审来源。此后的任何清理、契约测试阶段或功能，仍须作为 Active 基线中的独立步骤接受评审。
